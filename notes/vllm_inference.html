Local vLLM inference

Two related moves for v2: (1) replace the Sonnet teacher with a self-hosted open model on vLLM to generate SFT traces at compute prices instead of API prices, and (2) serve the Gemma student through vLLM so eval and GRPO rollouts stop being single-GPU / model.generate-bound. design + implementation plan

Thesis in one line For this task, generation is scrape-bound, not compute-bound. That makes a self-hosted vLLM teacher 1–2 orders of magnitude cheaper than the Sonnet API at corpus scale, and it makes a cheap GPU the right buy. The same vLLM serving layer also fixes the Gemma student's inference bottleneck. The one real risk is Gemma-4's head_dim=512 attention on non-Hopper GPUs — validate that first.

0 · Why this is clean to do here

The pipeline already decouples the teacher's wire format from the student. scripts/build_sft.py re-templates every captured trace into Gemma's native tool format, and the SFT/GRPO target is tool-call semantics + the final JSON — not the teacher's token stream. The Claude baseline is the existing proof: to_anthropic_tools in src/claude/claude_agent.py converts the same plain-callable tools from setup_tools() and drives an entirely different API, unchanged. Swapping in a vLLM teacher touches only trace generation; SFT, GRPO, schema, and the scrape backend are all untouched.

The bounded role of the teacher The teacher is only an SFT data generator. GRPO's reward is programmatic (schema-valid + item count) — no teacher in the loop. So teacher quality sets the student's ceiling for SFT and nothing else; if it under- performs, the cost is a weaker warm-start, not a broken pipeline.

1 · The economic case

Each episode is a multi-turn agentic loop whose context grows as scraped pages are fed back (you hit --max-length 32768 in v1). Rough per-episode: ~80–150k accumulated input tokens + a few k output.

PathUnit price~10k traces (est.)Notes
Sonnet API$3/M in, $15/M out~$3,000–4,000What v1 pays. Scales linearly with corpus size.
vLLM on RunPod$1–3/GPU-hr~$10–30 of GPUThroughput is scrape-bound (below), so a modest card kept busy clears thousands/hr.

Even assuming the local run is 3× slower and needs a bigger card, it stays ~100× under API spend. The hypothesis "compute is far cheaper than API credits" holds decisively at v2 corpus scale.

2 · The real bottleneck is the scrape IP, not the GPU

This reframes the whole sizing decision Each episode's wall-clock is dominated by scrape latency (headless Chromium: network-idle wait + auto-scroll = seconds per call), not token generation. CLAUDE.md already flags the ceiling: "the single egress IP can hit per-site rate-limits under a heavy corpus build." With continuous batching you can hold 30–100 episodes in flight against one vLLM server, at which point the GPU is underutilized and the scrape backend is the throughput ceiling and the ban risk.

Consequences:

  • Don't buy compute you can't use. You are not FLOP-bound during trace generation, so the fastest card is wasted money. Size for fitting the model + KV cache at your target concurrency.
  • The v2 scaling work is scrape parallelism (proxy rotation / a scrape worker pool / spread egress), not model serving. Plan that before 10×-ing the corpus, or the rate-limit wall caps you regardless of GPU.

Because it is scrape-bound, optimize $/hr and VRAM, not throughput/FLOPs.

Where "cheaper" backfires Don't undersize below the KV headroom your target concurrency needs. If the card only fits ~10 concurrent slots, the GPU idles waiting on the scrape latency you couldn't overlap, wall-clock stretches, and you burn more GPU-hours than the bigger card would have. Optimum: cheapest card × int4 quant × enough KV to keep ~30–50 episodes in flight, then spot pricing on top.

4 · Implementation — the shared OpenAI-compatible runner

vLLM exposes an OpenAI-compatible server, so a single new runner drives both the vLLM teacher (Qwen/Hermes) and, later, the Gemma student — they're just different base_urls. It mirrors claude_agent.py structurally: convert the tools once, then a manual tool loop.

4a · Tool translation (to_openai_tools)

Same shape as _callable_to_anthropic, different envelope. Reuses the callables from setup_tools() verbatim.

_JSON_TYPES = {str: "string", int: "integer", float: "number", bool: "boolean"}

def _callable_to_openai(fn) -> dict:
    props, required = {}, []
    for name, p in inspect.signature(fn).parameters.items():
        props[name] = {"type": _JSON_TYPES.get(p.annotation, "string")}
        if p.default is inspect.Parameter.empty:
            required.append(name)
    return {"type": "function", "function": {
        "name": fn.__name__,
        "description": inspect.getdoc(fn) or "",
        "parameters": {"type": "object", "properties": props, "required": required},
    }}

def to_openai_tools(tools): return [_callable_to_openai(t) for t in tools]

4b · The loop (src/vllm/openai_agent.py)

from openai import OpenAI

def run_episode(client, model, restaurant_name, tools, registry, system_prompt,
                max_tool_calls=8, max_tokens=16384):
    oai_tools = to_openai_tools(tools)
    messages = [{"role": "system", "content": system_prompt},
                {"role": "user", "content": restaurant_name}]
    for step in range(max_tool_calls + 1):
        out_of_budget = step == max_tool_calls
        resp = client.chat.completions.create(
            model=model, messages=messages, max_tokens=max_tokens, temperature=0.0,
            tools=None if out_of_budget else oai_tools,
            tool_choice=None if out_of_budget else "auto",
        )
        msg = resp.choices[0].message
        if out_of_budget and messages[-1]["role"] == "tool":
            # deliver BUDGET_FINALIZE_INSTRUCTION the same way the other loops do
            messages.append({"role": "user", "content": BUDGET_FINALIZE_INSTRUCTION})
        if not msg.tool_calls:
            return (msg.content or "").strip()            # final answer
        messages.append(msg.model_dump())                  # assistant turn verbatim
        for tc in msg.tool_calls:
            args = json.loads(tc.function.arguments or "{}")
            out = registry[tc.function.name](**args) if tc.function.name in registry \
                  else f"Error: unknown tool {tc.function.name!r}"
            messages.append({"role": "tool", "tool_call_id": tc.id,
                             "name": tc.function.name, "content": out})
    return ""

Note the transport difference from the Gemma/Claude loops: the OpenAI schema uses standalone {"role":"tool"} messages keyed by tool_call_id (no bundling, no prefix-preservation constraint — that only matters for the Gemma training template, not for a teacher generating data).

4c · Serving the teacher

# Qwen3 (or swap in NousResearch/Hermes-3-Llama-3.1-70B)
vllm serve Qwen/Qwen3-32B-AWQ \
  --served-model-name teacher \
  --enable-auto-tool-choice --tool-call-parser hermes \
  --max-model-len 40960 --kv-cache-dtype fp8 \
  --max-num-seqs 48 --gpu-memory-utilization 0.92

# client
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")

Qwen3 and Hermes-3 both use vLLM's hermes tool-call parser. --max-num-seqs is the concurrency knob; raise it until the scrape IP (not the GPU) is the bottleneck. Run the vLLM server and the scrape browser on the same pod, or point scrape at the devbox — either way the scrape egress is the thing to watch.

6 · The Gemma student on vLLM (the inference worry)

The v1 eval was slow and fragile for a structural reason: eval_split.py forces --workers 1 because a single HF model.generate isn't thread-safe, and the SDPA math path OOMs on long context (it moved to an A100 for headroom). A vLLM server fixes both — it's concurrent by construction (continuous batching) and uses paged KV. This is the direct answer to "I'm worried about inference on this Gemma model": serve it once, raise the worker count, done. It also becomes the GRPO rollout engine later.

Validate this FIRST — same demon as the SDPA saga Gemma-4-E4B's global-attention layers have head_dim=512 (CLAUDE.md). That is exactly what broke FlashAttention-2 (caps at 256) and forced the whole SDPA GQA patch. vLLM's default attention backends inherit the same constraint:
  • On Hopper (H100/H200): FlashAttention-3 / FlashInfer handle head_dim ≥ 256 → should work. Validate the vLLM-Gemma path on the H200 you already have.
  • On Ampere (A100/A10, the current eval box): FA caps at 256 → may fail or fall back. Try VLLM_ATTENTION_BACKEND=XFORMERS (or Triton) and confirm it loads and produces correct output before trusting any speedup. Treat "does Gemma-4-E4B even serve on this card under vLLM" as the go/no-go gate.
Also confirm vLLM loads the model as Gemma4ForCausalLM (text-only path). Liger only supports gemma4_text, not the multimodal Gemma4ForConditionalGeneration wrapper — vLLM's text class is the one to target since we never use the vision/audio towers.

Recommended path: raw /v1/completions, keep our template + parser

Do not use vLLM's server-side chat/tool parsing for the student. vLLM ships no Gemma-4 tool-call parser, and the student was SFT'd on Gemma's exact native wire format (<|tool_call>call:NAME{…}<tool_call|>, the bundled tool_responses turn, the reasoning-guard prefix rules). Any re-templating risks drift from what it was trained on. Instead, let vLLM do only fast batched decode and keep rendering + parsing in our code, byte-identical to agent.py:

# render locally with the SAME chat template used in training, then send the string
prompt = tokenizer.apply_chat_template(
    messages, tools=tools, add_generation_prompt=True,
    enable_thinking=True, tokenize=False)            # -> str

comp = client.completions.create(
    model="gemma-menu", prompt=prompt,
    max_tokens=4096, temperature=0.0,                # == do_sample=False
    stop=["<tool_call|>"],                            # == agent.py stop_strings
    extra_body={"add_special_tokens": False})        # template already emits BOS
text = comp.choices[0].text
parsed = tokenizer.parse_response(text)              # OUR parser, unchanged

This is a drop-in swap of generate_turn in agent.py: model.generate(...) → one /v1/completions call, everything else (the tool loop, the bundled tool_responses turns, the parse-failure recovery, budget finalize) stays exactly as written. The template never leaves our control, so training/inference stay matched — and the loop is now safe to run concurrently against the server, so eval workers can go > 1.

7 · Validation plan (before committing to a v2 corpus)

  1. Teacher quality gate. Serve Qwen3-32B (and/or Hermes-3-70B) on the H200, run the same seed-42 plan for 30–50 episodes through eval_split.py --model vllm, score against the existing Sonnet numbers (schema-valid 99.4%, found 95.0%, mean items 39.0). Greenlight if within ~5–10% on found% and mean-items; else go bigger (70B → MoE-235B) rather than distilling a weak teacher.
  2. Gemma-serve gate. Confirm the merged student loads and generates correct output under vLLM on the target card (H200 first; Ampere only with the XFORMERS backend confirmed). Compare a handful of episodes' JSON to the HF model.generate path — they should match at temperature 0.
  3. Throughput gate. With Gemma served, raise eval_split.py workers and confirm wall-clock drops and the scrape IP becomes the limiter — that's the signal the inference bottleneck is gone.
  4. Scale. Only then run the full teacher corpus on the cheap A100 spot box.
