RunPod Training Handoff

Fine-tune google/gemma-4-E4B-it (LoRA / bf16) on the menu-extraction SFT corpus, on a single H100 SXM, then push the adapter + merged model to S3. for the setup agent

Mission in one line Provision 1× H100 SXM on RunPod, rebuild the SFT dataset from the S3 corpus, run scripts/train_sft.py, measure whether the run is compute- or memory-bound, and push the outputs to S3 from the pod. Report the diagnostic numbers so the human decides whether/how to scale.

2 · Scoped AWS credentials for the pod (this enables push-from-pod)

Security rule The devbox uses an EC2 instance profile — that identity does not exist on a RunPod pod, and the project rule is no long-lived static keys. Mint short-lived, least-privilege credentials scoped to just this bucket/prefix.

Recommended — temporary STS credentials (~12 h, covers the run, then auto-expire):

  1. Create (or reuse) an IAM role/user whose policy is exactly the S3 access below (nothing else).
  2. Mint temp creds and inject the three AWS_* values into the pod env: 
    # if it's a role you can assume:
aws sts assume-role \
  --role-arn arn:aws:iam::<acct>:role/<menu-corpus-pod-role> \
  --role-session-name gemma-sft-pod \
  --duration-seconds 43200        # 12h

# or, if your CLI identity is an IAM user (creds inherit the user's perms):
aws sts get-session-token --duration-seconds 43200

Least-privilege policy (read the corpus, write the model outputs):

{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "List", "Effect": "Allow", "Action": ["s3:ListBucket"],
      "Resource": "arn:aws:s3:::restaurant-menu-corpus",
      "Condition": { "StringLike": { "s3:prefix": ["v1/*"] } } },
    { "Sid": "ReadCorpusWriteModels", "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::restaurant-menu-corpus/v1/*" }
  ]
}

Fallback if role/STS setup is heavy: create a dedicated IAM user with this inline policy + one access key, use it, and delete the key when training finishes. Never commit it or bake it into an image.

Get the SFT dataset onto the pod

Primary — pull the prepared dataset from S3 (already built: 60.6 MB, 948 examples). No traces pull, no tokenizer, no rebuild:

mkdir -p data/sft
aws s3 cp s3://$S3_BUCKET/$S3_PREFIX/sft/train.jsonl data/sft/train.jsonl
wc -l data/sft/train.jsonl        # expect 948

Integrity: the object carries its md5 as metadata (x-amz-meta-md5, = 07dd4615bf1cb27f04697e77fe040f0c) — compare with md5sum data/sft/train.jsonl if you want to be sure.

Fallback — rebuild from traces (only if you must regenerate it) Deterministic (seed 42 + the version-controlled reject-list); needs the gated tokenizer (HF login above): 
uv run python scripts/cache_sync.py pull --only traces      # 73 MB of traces
uv run python scripts/build_sft.py --reject-list data/review/reject_list.txt
# -> ~948 written to data/sft/train.jsonl (1000 traces - 50 rejected - 2 unparseable)

4 · Dry-run (no GPU) — confirm the dataset + mask

uv run python scripts/train_sft.py --data data/sft/train.jsonl --dry-run --eval-frac 0.05

This builds + masks the dataset and prints the token-length distribution and one masked example, without loading the model. Confirm the kept-count and that the "TRAINED (loss) tokens" look like the assistant tool-calls + final JSON only.

5 · Launch training — SINGLE GPU (different from the 2-GPU recipe!)

Do not use accelerate/torchrun here The configs/accelerate_ddp.yaml + accelerate launch recipe in notes/runpod_sft.md is for 2 GPUs. On one GPU, run plain uv run python — a single process. Launching under accelerate/torchrun with the DDP config on 1 GPU is wrong. 
uv run python scripts/train_sft.py \
  --data data/sft/train.jsonl \
  --output-dir /workspace/gemma-menu-sft \
  --eval-frac 0.05 \
  --num-train-epochs 3 \
  --logging-steps 5 \
  --num-processes 1 \
  --max-length 8192          # START SMALL — see §6, then ramp up

Effective batch on 1 GPU = per_device(1) × grad_accum(8) × 1 = 8. --num-processes 1 only fixes the printed batch math. Leave --attn sdpa (default).

6 · The core task: is it compute- or memory-bound?

Why this decides how to scale Plain DDP replicates the model on every GPU — it splits the batch, not a single sequence's activations. So:
  • Memory-bound (can't reach the target --max-length): adding more H100s via DDP does not help — each GPU still holds one full-length sequence. You need more memory per device (H200 = 141 GB), a lower --max-length, or FSDP/chunked-loss.
  • Compute-bound (fits, GPU pinned ~100%): add GPUs (DDP, ~linear) to cut wall-clock.

The dominant memory term is the loss logits: seq_len × vocab(~256k) × 4 bytes (fp32). At 32k tokens that alone is tens of GB, transient, per sequence — this, not the 4B weights, is what pushes an 80 GB card. And because over-length examples are dropped (not truncated), the max --max-length you can fit directly sets how much of the corpus you train on:

--max-lengthexamples kept (of 948)dropped
8192~636 or fewermost; pipeline test only
16384~63632.9%
32768~78617.1%

Diagnostic protocol

  1. With --max-length 8192, confirm it trains and checkpoints. In a second shell watch: 
    watch -n1 nvidia-smi                 # memory used vs 80GB, GPU-util %
# or: nvidia-smi dmon -s um          # SM-util + mem columns, 1 Hz
  2. Note peak memory and the logged it/s once ~10–20 steps have passed (that's your throughput; ETA ≈ steps × sec/step).
  3. Ramp --max-length: 8192 → 16384 → 32768, relaunching each time. Find the largest value that trains without CUDA OOM. That's the memory ceiling on 1× H100.
  4. Classify:
    • Fits 32768, GPU-util pinned ~95–100%, memory has headroom → compute-bound. One H100 is enough for the full corpus; add GPUs only to go faster.
    • OOMs before 32768 (or you had to shrink to fit and util is spiky/<90%) → memory-bound. Record the ceiling.
Record these numbers for the human max feasible --max-length on 1× H100 · peak GPU memory at that length · GPU-util % · it/s · est. wall-clock for 3 epochs · final train & eval loss.

Decision matrix (hand back to the human, don't self-escalate spend)

ObservationBoundRecommended scale-up
Fits 32k, util ~100%, want it fasterCompute2–4× H100 with the existing DDP recipe (accelerate launch --config_file configs/accelerate_ddp.yaml, set num_processes=GPUs). Near-linear speedup.
Fits 32k, util ~100%, ~1–2 h is fineComputeStay on 1× H100. Done.
OOM before 32kMemoryMove to 1× H200 (141 GB) to reach 32k (keeps 83% of data), OR accept a lower --max-length on H100 (fewer examples), OR (advanced) enable a chunked/fused cross-entropy to shrink the logits term. More H100s via DDP will not fix this.

7 · Push outputs to S3 (from the pod)

On completion, train_sft.py writes two local dirs under --output-dir:

/workspace/gemma-menu-sft/adapter/LoRA adapter + tokenizer (small, ~tens of MB)
/workspace/gemma-menu-sft/merged/base+adapter merged bf16 HF model + tokenizer (several GB) — what eval_split.py --model-path loads

Nothing auto-pushes. Using the scoped creds from §2:

# push the adapter FIRST as insurance (tiny), then the merged model
DEST="s3://$S3_BUCKET/$S3_PREFIX/models/gemma-menu-sft-$(date +%Y%m%d)"
aws s3 cp --recursive /workspace/gemma-menu-sft/adapter "$DEST/adapter"
aws s3 cp --recursive /workspace/gemma-menu-sft/merged  "$DEST/merged"
aws s3 ls "$DEST/" --recursive | tail        # verify
Ephemeral pod Get the outputs to S3 before tearing the pod down. Even on the /workspace volume they vanish if the volume is deleted. Verify the aws s3 ls shows the merged safetensors before stopping the pod.

8 · Done criteria / report back

  • ✅ train.jsonl rebuilt (~948) and dry-run mask looked correct.
  • ✅ Training completed 3 epochs (or you stopped early with a clear reason); final train + eval loss captured.
  • ✅ Bound classified with the numbers in §6, plus a one-line recommendation from the decision matrix.
  • ✅ adapter/ and merged/ pushed to S3; paths reported.

Appendix · Gotchas that will bite you

Attention Keep --attn sdpa. Gemma-4-E4B's global layers use head_dim=512; FlashAttention-2 hard-caps head_dim at 256 (throws on the global layers), and there's no stable FA3 head_dim=512 training path even on Hopper/H100. SDPA's mem-efficient kernel (with the repo's GQA patch, already applied in model.py) is the one that serves 512-dim heads. Don't add flash-attn.
  • Gated model: both build_sft.py (tokenizer) and training download google/gemma-4-E4B-it — HF login is required or they fail.
  • Single vs multi-GPU launch: 1 GPU → plain uv run python scripts/train_sft.py …. Multi-GPU → accelerate launch --config_file configs/accelerate_ddp.yaml … with num_processes = GPU count. The trainer omits device_map on purpose so accelerate can place the model; don't add one.
  • Driver/CUDA: torch is cu128 — if torch.cuda.is_available() is False, the host driver is too old for CUDA 12.8; pick a newer RunPod image.
  • No static AWS keys anywhere persistent. Temp STS creds only; they expire on their own. Delete any fallback IAM access key after the run.
  • uv only — never bare python/pip; reproduce the env with uv sync.
  • Data prep is deterministic — if you ever need to re-run build_sft.py, same seed + same reject-list → same 948 rows.
