Lessons already paid for (the expensive ones):

- The v1 student's dominant failure was **empty output (non-termination), not menu quality** — its menus are teacher-quality when it finishes.
- **Serving fidelity dominates**: 4-bit serving of a bf16-trained checkpoint cost ~32 points of success (24%→56%). Always serve merged bf16.
- **A prompt rule fixed most of the rest**: `_ALWAYS_ANSWER_RULE` in [src/prompts.py](src/prompts.py) took success 56%→**88%** / empty 38%→**12%** on the same 50 episodes (16 fixed, 0 regressed), and revealed that dietary-conditioned episodes were mostly a *termination* failure too (7/20→17/20).
- **GRPO moved the policy but not the task.** Run 2 (lr 1e-5, G=16, 2×B200) drove `‖B‖` 13× further than run 1 in half the steps, and the held-out probe stayed flat at ~0.53 while `clipped_ratio` fell 0.32→0.20 — the policy learned to *finish inside its budget*, not to build better menus. The standing hypothesis is that the reward is the problem, not the optimizer: the grounding term pays for faithfulness to scraped evidence, which is maximized by reporting **fewer** items (`item_count_delta` got worse, −5.8 → −6.6), while the actual gap is recall. **If RL is ever revisited, re-weight the reward for completeness first — do not just run more steps.**

## Hardware constraints (these drive real code decisions)

Dev runs on an **Ubuntu instance with a 24 GB GPU** (e.g. RTX 3090/4090 / A10). With 24 GB the model is no longer VRAM-bound the way the old 6 GB laptop was, so some earlier constraints have relaxed:

- **`torch` is pinned to the CUDA `cu128` wheel index** via `[[tool.uv.index]]` + `[tool.uv.sources]` in [pyproject.toml](pyproject.toml). `explicit = true` means only torch uses it; everything else is PyPI. Drop to `cu126` only if the instance driver is unusually old.
- **bf16 fits in *VRAM* (~8–9 GB weights), but host RAM is the real bottleneck on this box: only ~15 GB total and no swap.** Loading bf16 materializes the full ~15 GB of weights in host RAM on the way to the GPU, which on a 15 GB box thrashes the page cache and makes the load crawl (re-reading the safetensors blob from disk) — *much* slower than the VRAM math suggests. 4-bit (`BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4", bnb_4bit_compute_dtype=torch.bfloat16)`, ~3.5 GB) streams the weights down on load and sidesteps the cliff — that's why [main.py](main.py) defaults to `--quantize` here. [src/gemma/model.py](src/gemma/model.py) passes `low_cpu_mem_usage=True` for the bf16 path to cap peak host usage, but on a bigger-RAM instance bf16 is the better choice for full quality (and for leaving VRAM free for QLoRA training/RL batches, prefer 4-bit). If loads are still slow or OOM, check for an orphaned python still pinning the whole model in VRAM (an interrupted run often leaves one) — find it with `nvidia-smi` and `kill` it.
- **Use `device_map={"": 0}`, not `device_map="auto"`.** Pin to GPU 0 explicitly; `"auto"` can still offload across devices in ways you don't want. (On the old 6 GB card `"auto"` silently dumped the whole model to CPU — symptom: `Model loaded on: cpu`, `0.00 GB VRAM`, generation hangs.)
- **Attention backend: use `sdpa`, not FlashAttention-2.** *(HF/transformers path ONLY — **vLLM handles `head_dim=512` natively** via FA4 and needs none of this; see "vLLM serving". Don't carry this constraint over to vLLM.)* FA2 is *incompatible with this model*: Gemma 4 E4B's global-attention layers use `head_dim=512` (`global_head_dim` in `config.json`; the sliding layers are 256), and FlashAttention-2 hard-caps head_dim at **256** on every GPU — so `attn_implementation="flash_attention_2"` loads but throws `FlashAttention forward only supports head dimension at most 256` at the first global layer. FA3/FA4 support larger head dims but require **Hopper** GPUs (H100); the 24 GB dev card is Ampere/Ada, so they don't apply either. Net: pass `attn_implementation="sdpa"` (torch built-in, no extra dep) — it handles 512-dim heads by falling back from its flash kernel to the mem-efficient/math path, and it's the default (`--attn sdpa|eager` on [src/gemma/run_agent.py](src/gemma/run_agent.py), applied in [src/gemma/model.py](src/gemma/model.py)'s `load_model`). Don't add a `flash-attn` dependency; it can't run this model. (Reaching for FA2 would also force a torch downgrade to ≤2.8, since no FA2 wheel is built for torch 2.11 and a source build OOMs this 15 GB / no-swap box — another reason to stay on `sdpa`.)
- **`sdpa` needs a GQA patch or it OOMs on long context.** With plain `sdpa`, Gemma 4's global layers (`head_dim=512`, GQA: 8 query / 2 KV heads) hit a transformers heuristic (`use_gqa_in_sdpa`) that, for mask-free causal layers, keeps KV un-expanded and passes `enable_gqa=True`. PyTorch's mem-efficient kernel **can't do the GQA broadcast at head_dim=512** on Ampere/Ada, so SDPA silently falls to the **MATH** backend and materializes the `(1, 8, S, S)` score matrix — measured OOM at ~14k tokens (baseline 13 GB at 6k, then OOM). [src/gemma/model.py](src/gemma/model.py)'s `load_model` fixes this by forcing the `repeat_kv` path (`use_gqa_in_sdpa → False`): with matched head counts the efficient kernel serves head_dim=512, and **default SDPA dispatch picks it on its own — no `sdpa_kernel(...)` override** (an explicit one was a no-op; the GQA broadcast, not kernel priority, was the disqualifier). Result: prefill stays **linear** in S (12.2 GB @ 14k, 13.5 GB @ 20k) instead of OOMing. `flex_attention` is *not* an alternative here — its Triton kernel exceeds Ampere/Ada shared memory at head_dim=512.

## Library version gotchas (transformers 5.x)

- `tokenizer.apply_chat_template(..., return_tensors="pt")` returns a **`BatchEncoding` dict**, not a bare tensor. Pass `return_dict=True` and call `model.generate(**inputs, ...)`; get the prompt length from `inputs["input_ids"].shape[-1]` to slice off the prompt when decoding.
- `apply_chat_template(..., tokenize=True)` **without** `return_dict` returns a **`tokenizers.Encoding`**, not a `list[int]` — read `.ids`, or pass `return_dict=True` and take `["input_ids"]`. (Easy to trip over when checking token-level prefix properties.)

## Gemma 4 chat template & tool calling

Gemma 4's template differs from Gemma 2/3 — verify behavior against the live tokenizer (render with `apply_chat_template(..., tokenize=False)`; cf. the `__main__` block in [src/gemma/agent.py](src/gemma/agent.py)) rather than assuming older-Gemma conventions. What we confirmed:

- **System role is supported natively** (`<|turn>system ... <turn|>`). No need to fold system text into the first user turn (that was a Gemma 2/3 limitation).
- **Define tools as plain Python functions** (typed signature + Google-style docstring) and pass them via `apply_chat_template(tools=[...])`. transformers auto-converts them to Gemma's schema; do **not** hand-write the tool-declaration string. System prompt and tool declarations coexist in the same system turn.
- **Wire format** (special tokens, not normal JSON — note `<|"|>` is the string delimiter and types are uppercase like `STRING`/`OBJECT`):
  - Declaration (system block): `<|tool>declaration:NAME{...}<tool|>`
  - Model emits a call: `<|tool_call>call:NAME{arg:<|"|>value<|"|>}<tool_call|>`
  - Tool result fed back: the loop appends the **bundled** form `{**parsed, "tool_responses": [{"name": NAME, "response": ...}]}` (the assistant turn carries both its `tool_calls` and their responses), which renders as `<|tool_response>response:NAME{value:<|"|>...<|"|>}<tool_response|>`. **A standalone `{"role": "tool", ...}` message renders only if it immediately follows an assistant turn with an *open* (unanswered) `tool_call`** — appended after a completed bundled turn (or as the first turn) it is **silently dropped (+0 tokens)**, and the response is always labeled by the preceding `tool_call`'s name (the message's own `name` is ignored). This is why the parse-failure recovery synthesizes an assistant tool-call turn rather than appending a bare tool message (see Prefix-preservation).
- **Parsing the model's output: decode with `skip_special_tokens=False`.** The `<|tool_call>` markers are special tokens — the default `skip_special_tokens=True` deletes them, so the loop would never see that a tool was called.

## Prefix-preservation & GRPO-readiness

Verified (tokenizer-only) that Gemma 4's template is **prefix-preserving for single-task agentic trajectories**: rendering `[m₀…mₖ]` is an exact token-prefix of `[m₀…mₖ, mₖ₊₁]` across `system → user → (assistant tool_call → tool response)* → final`, with or without `reasoning` traces. So **TRL's GRPO tool loop works on the stock template — no patched training template needed** (unlike Qwen3/DeepSeek-V3, which TRL auto-patches; Gemma 4 is not on that list).

The one way it breaks: the template's *reasoning guard* renders `reasoning`/`reasoning_content` only for assistant turns **after the last user message** (earlier ones are stripped via a `strip_thinking` macro). So a **mid-episode user turn rewrites earlier tokens** and breaks the prefix. Consequences:

- **Parse-failure recovery in [src/gemma/agent.py](src/gemma/agent.py).** On a `parse_response` failure (e.g. the model degenerates into a recursive/truncated `jsonOptions.schema` blob), `run_episode` feeds the error back as a **synthesized assistant tool-call turn carrying a tool response** — *not* a user turn (would break the prefix) and *not* a bare `{"role": "tool"}` message (silently dropped after a bundled turn → with greedy decoding the model just re-emits the same bad output). The recovery turn's tool name is regex-extracted from the malformed wire text (`call:NAME{…}`), falling back to the first registered tool.
- If you capture this loop's traces for SFT, they re-render consistently with how they'd appear in training.
- The thinking field the template reads is **`reasoning` / `reasoning_content`**, not `thinking`. `tokenizer.parse_response` may surface it under a different key — verify the round-trip if you need reasoning carried across tool turns in the inference loop.

## Context distillation (the SFT approach)

**Goal: the SFT stage should use context distillation, not a matched-prompt copy.** Behavioral guidance that shapes *how* the agent works but does **not** change *what the correct menu is* belongs in the **teacher** prompt only; the **student** is trained on the teacher's trajectories under the *student* prompt (which omits that guidance), so the behavior is baked into the weights instead of carried in the prompt at inference. That guidance is the single teacher-only block **`_TEACHER_GUIDANCE`** in [src/prompts.py](src/prompts.py), which bundles four HOW-not-WHAT nudges: **scrape strategy** (direct-first, browser-fallback, keep the fuller result), **persistence** (don't give up after one search), **identity verification** (confirm the scraped page is the same restaurant — name + city/address — before extracting; added to attack harvest name-mismatch and wrong-city failures), and **source selection** (prefer the restaurant's own site, avoid DoorDash/Uber Eats/Grubhub/Yelp). The bare tool-loop orientation (`_SHARED_TOOL_ORIENTATION`: search returns links, scrape reads a page, *you* write the JSON) is **shared** — it biases neither source nor mode — as is the `mode` mechanic itself, which lives in the `scrape_url` docstring (identical across variants).

- **The rule that matters is `student-train-prompt == student-inference-prompt`, not `teacher == student`.** The teacher is just a data generator; its prompt can be richer. What you must never do is train the student on a target that is only correct given text the student never sees.
- **Safe to make teacher-only:** nudges that don't change the target (scrape strategy, persistence, identity verification, source selection — all of `_TEACHER_GUIDANCE`). **Must be identical across variants:** anything that defines the task or the correct output — the JSON schema, the **food-only scope rule** (`_SCOPE_RULE`: it changes *which items belong*, so despite looking "behavioral" it is target-defining and stays shared), the tool set/declarations, and the **dietary restrictions** (an input-conditioned instruction: drop it from the student and a filtered-menu target becomes incoherent). `build_system_prompt` enforces this by construction — `variant` gates *only* `_TEACHER_GUIDANCE`; every other block is shared.
- **`variant="teacher"` is the default** everywhere (`SYSTEM_PROMPT`, `setup_tools`, both runners' `--prompt-variant`, the viz dropdown) — it's what we test on and what generates SFT data. Switch to `student` to preview the distillation-target prompt.
- **Data, not the prompt trick, carries the behavior:** the SFT set must *contrastively* exhibit it (search returns a delivery-app URL **and** a better source; the teacher picks the better one), or the student learns "scrape result #1" instead. Hold out an eval that checks the **student** (no guidance) still avoids the delivery apps; if it doesn't distill, add contrastive data rather than leaking the guidance back into the student prompt. GRPO's completeness reward later reinforces the same preference from the outcome.

## Web tools (Brave search + local Chromium scrape)

The agent sources two live tools — **`web_search` backed by Brave (REST), `scrape_url` backed by a local headless Chromium** (no scrape API/key). The model only ever sees two generically-named tools with fixed, vendor-neutral docstrings (`web_search`/`scrape_url`) — no provider name leaks into the SFT/GRPO training data the tool calls get baked into. The pieces:

- **[src/backends.py](src/backends.py)** — the network seam. `build_search()` returns a Brave-backed `search(query) -> str` (`GET /res/v1/web/search`, `X-Subscription-Token` auth); `build_scrape()` returns a local `scrape(url, mode="direct") -> str`. **`mode`:** `"direct"` is a plain `requests` GET (no browser/JS) — instant and complete for server-rendered pages — that **escalates to a no-scroll browser render** if the fetch comes back a thin CSR shell (< `DIRECT_MIN_CHARS`); `"browser"` is a headless-Chromium render that waits for network-idle then **auto-scrolls to the bottom** so scroll-lazy-loaded menus (Square/Toast/own-sites) render fully. Both return markdown (HTML stripped of script/style/etc. via BeautifulSoup + markdownify). The model tries `"direct"` first and escalates to `"browser"` (see the `scrape_url` docstring + `_LIVE_RULES` in [src/prompts.py](src/prompts.py)). Navigation/render failures return a readable `"(scrape failed …)"` string, never raise, so one bad URL can't kill an episode. `search` pins `count=SEARCH_RESULT_LIMIT` through one shared `_format_results`. These functions return **un-capped** strings.
  - **Baked-in scrape protections** (properties of the backend, so no caller's wiring can drift): **(1) slim at the source** — `_slim_scrape` (base64 `data:` URIs, images, empty links/bullets, NUL bytes) is applied inside `build_scrape`, so every consumer returns/caches the slimmed body (it used to live in `setup_tools`, which let `warm_cache`'s own cache wrap store RAW rows); **(2) dead ends answer instantly** — `skip_reason(url)` returns a deterministic model-facing sentinel for `SKIP_DOMAINS` (bot-walled delivery apps/Yelp/OpenTable/socials/SEO farms), `SKIP_EXTENSIONS` (.pdf/images), and (via a Content-Type check on the direct fetch) extension-less binary payloads — the sentinels are deliberately under `cache.MIN_CONTENT_CHARS` and match no failure marker, so they classify `'empty'` = a **permanent** cached negative (an `'error'` row is a live-policy miss that would re-pay a 30-45s bot-wall timeout on every pass); **(3) per-host throttle** — network fetches to one host are spaced `DOMAIN_MIN_INTERVAL_S` apart process-wide (cache hits unaffected), protecting live GRPO's parallel rollouts from single-IP rate-limits; **(4) infra circuit breaker** — `INFRA_STREAK_ABORT` (15) consecutive infra-failed scrapes raise `BrowserDeadError`, so a browser that dies **mid-run** aborts the sync callers via their per-episode breakers (a broken-from-the-start browser is caught cheaper by `preflight_browser`, which `build_corpus`/`warm_cache`/`eval`/`train_grpo` all run when the cache policy isn't `canned`). **TRL is the exception**: its tool loop catches tool exceptions (`except Exception` + `gather(return_exceptions=True)`) and feeds `{"error": ...}` back as the tool message, so in GRPO the raise surfaces as a saturated `tools/failure_frequency` metric instead — [scripts/train/train_grpo.py](scripts/train/train_grpo.py)'s `ToolFailureAbort` callback watches that metric and stops training (gracefully — the adapter save still runs) when it stays ≥0.8 for 3 logging steps. Site failures (timeouts etc.) reset the streak and stay cacheable facts; **(5) render watchdog** — every browser render runs under a `RENDER_WATCHDOG_S` (180s) hard wall-clock cap. `page.goto`/`networkidle` have their own timeouts, but `page.evaluate` (the auto-scroll), `page.content()`, and context open/close are protocol calls with NO client-side timeout — a page whose renderer wedges blocks the call forever (measured 2026-07-25: all 3 warm workers parked 30+ min, idle CPU, no sockets). The watchdog kills that thread's node **driver** (the only reliable lever — the sync API is greenlet-bound, so no other thread can close the browser politely; `_driver_proc` reaches the pid via guarded private API), the blocked call raises, and the failure is rewritten to a `render watchdog:` **site**-class error (cacheable, non-infra). **Everything after the kill must assume the driver is GONE**: a protocol call against a dead driver does not raise, it *hangs* — Playwright's sync wrapper is `while not task.done(): fiber.switch()`, a busy spin that pins a core **and holds the GIL**, so the main thread starves and Ctrl+C is never delivered (measured 2026-08-05: an unkillable warm with all 3 workers inside `new_context()`/`close()` and every driver already dead). So the watchdog path skips `context.close()` and calls **`_forget_thread_browser()`**, which drops the thread-local refs and deregisters from `_POOL_REGISTRY` (so `close_pool()` can't hang at exit either). **The distinction that matters there is protocol call vs transport call**: `browser.close()` must NOT be called (it awaits a driver *response* → hangs), but `pw.stop()` MUST be (it is transport teardown — `request_stop()` closes the pipe, `wait_until_stopped()` awaits a reader task that already ended at EOF). Skipping `stop()` leaves the thread's asyncio loop running — `BaseEventLoop.run_forever` only clears asyncio's running-loop marker in its `finally` — and Playwright then refuses to start a second loop on that thread (`Sync API inside the asyncio loop`), **poisoning the worker for the rest of the run**: measured 2026-08-06, one wedged page cost 585 infra failures and aborted the warm with 5 `BrowserDeadError`s. If `stop()` itself fails, `_clear_running_loop()` resets the marker by hand (leaking the old loop beats losing the worker). This is required because **`is_connected()` cannot detect a killed driver**: it returns a cached flag that only a close *event* clears, and a force-kill sends none. The next call then sees an empty pool and launches fresh.
  - **The browser uses a THREAD-LOCAL pooled Chromium** (`_pooled_browser`/`_render_pooled`/`close_pool`): a sync Playwright browser is bound to its creating thread, so each thread launches one Chromium and reuses it across calls (fresh context per call for isolation; ~0.5s/call saved after warmup). This is why it's safe both from the sync agent loops and from the viz server (whose `/api/extract` is a sync `def` → FastAPI threadpool worker, no running event loop). **Do not** make that endpoint `async def` without moving the scrape onto its own thread. Chromium launches with `--disable-http2` (dodges `ERR_HTTP2_PROTOCOL_ERROR` on some CDNs, e.g. mcdonalds.com) + `--no-sandbox`. Needs `playwright install chromium` + its system libs.
  - **Why a browser at all for "direct"**: a bare `requests` GET of a client-rendered SPA (`*.square.site`) returns ~30 chars of empty shell, so requests alone can't handle CSR sites — the shell-detection fallback to a no-scroll render is what makes the direct path work there. **Limits:** does not beat bot-protection (DoorDash/Yelp detect headless Chromium) or recover *virtualized* lists (recycled DOM nodes); the single egress IP can hit per-site rate-limits under a heavy corpus build.
- **[src/tools.py](src/tools.py)** — `setup_tools()` calls `build_search()`/`build_scrape()` and wraps them via `build_model_tools` into two **plain Python functions** (`web_search`/`scrape_url`) with fixed, vendor-neutral docstrings. They're ordinary callables with typed signatures + docstrings, so `apply_chat_template(tools=...)` and the Claude runner's `to_anthropic_tools` consume them directly. The wrappers add the `MAX_TOOL_CHARS` cap (with a non-silent truncation warning) and nothing else. **Caching (Phase 2 — see [notes/phase2_plan.md](notes/phase2_plan.md)) lives in [src/cache.py](src/cache.py)**: a content-addressed **SQLite** cache that wraps the two *backend* closures (`build_search`/`build_scrape`) *before* the cap is applied. `build_scrape` slims its own markdown at the source (`backends._slim_scrape` — strips base64 `data:` URIs, images, empty links/bullets, NUL bytes), so a new scrape **caches (and returns) a slimmed but uncapped body** — junk removal is baked in, while only the `MAX_TOOL_CHARS` *cap* stays retunable without re-scraping (`clean_cache.py` retro-applies the same slim + a status **reclassify** (`Cache.reclassify` — `slim_rows` rewrites the text only, so a raw-classified `'ok'` would otherwise stay stale forever) + a `MAX_STORED_CHARS`=400K clip to a cache built earlier — the pilot cache went 2.15 GB → 339 MB). search results are **not** slimmed (the model mines them for URLs). It has a pluggable **miss policy** (`live | canned | error`) so one code path serves SFT (live-fallback), GRPO (frozen/canned), and the product. The DB lives at `data/cache.sqlite` (git-ignored; source of truth is S3).
- **`BRAVE_API_KEY`** is required — `build_search` raises a `SystemExit` if it's missing; **scrape needs no key**. Loaded from a repo-root **`.env`** by [src/gemma/run_agent.py](src/gemma/run_agent.py) via `python-dotenv`. `.env` is git-ignored; commit [.env.example](.env.example) instead.
- **No Node/`npx`, no vendor scrape SDK** — search is a plain `requests` call; scrape is local Playwright. Project deps: `requests`, `python-dotenv`, `playwright`, `markdownify`, `beautifulsoup4`. (The old `mcp`/`firecrawl-py` deps, `src/mcp_client.py`, and the earlier Jina/hybrid/per-call scrape variants were removed when the local backend was finalized.)
- **Measured (Kashish Kirkland, end-to-end):** the local scrape pulls the full `/s/order` page in one `browser` call → **10 sections / ~86 items in ~3 tool calls**, and generalizes across platforms (Pagliacci 211 price markers, Serious Pie 85, a fresh Square order site 113); bot-walled chains (McDonald's) fail gracefully. Going local (vs the earlier Jina scrape) buys **determinism**: Jina's server-side cache returned 351 chars cold then 15,069 warm for the same URL — a reproducibility hazard for SFT/GRPO that self-hosting removes.

## Claude baseline (Anthropic API)

A second runner drives **Claude Sonnet** (`claude-sonnet-5`, in [src/claude/claude_agent.py](src/claude/claude_agent.py)) through the same task, so we can compare a frontier model against Gemma on identical inputs. The point is parity: it reuses the *same* tool source, system prompt, and JSON contract — only the model and the transport differ.

- **Shared everything.** [src/claude/run_claude.py](src/claude/run_claude.py) calls the same `setup_tools()` from [src/tools.py](src/tools.py) (live Brave search + local scrape) and the same `SYSTEM_PROMPT`, and validates with the same `schema.extract_json`. The tool *registry* (`name -> callable -> str`) is used as-is; only the tool *declaration* format is translated.
- **Tool translation.** The tools are plain Python callables (typed signature + docstring); the Anthropic API wants `{"name","description","input_schema"}`. `to_anthropic_tools` in [src/claude/claude_agent.py](src/claude/claude_agent.py) derives that from each callable's signature/docstring (the old OpenAI-style function-dict branch is gone with MCP), so the same `setup_tools` result drives Claude unchanged. `uv run python src/claude/claude_agent.py` prints the converted declarations (no key/network needed).
- **The loop** is a standard manual agentic loop over `client.messages.create` (no transformers, no GPU): call → run `tool_use` blocks via the registry → feed `tool_result`s back → repeat. Adaptive thinking is on (`thinking={"type":"adaptive"}`); the full assistant turn (thinking + tool_use blocks) is appended verbatim each round, as the API requires. Same budget as the Gemma loop (`MAX_TOOL_CALLS=8`, `MAX_TOKENS=16384`). **Budget exhaustion (both loops):** on the final turn each loop injects `BUDGET_FINALIZE_INSTRUCTION` (in [src/prompts.py](src/prompts.py)) telling the model to emit the JSON from what it already gathered (a partial menu with `found=true` beats an empty reply — and is better SFT data). The Claude loop delivers it by appending a text block to the last tool-results turn and dropping `tools`; the Gemma loop can't hard-drop declared tools, so it delivers the instruction via a **synthesized assistant tool-call carrying it as a `tool_response`** — the same prefix-preserving carrier the parse-failure recovery uses (a bare user turn would break GRPO prefix-preservation; see "Prefix-preservation").
- **Keys & deps.** Requires `ANTHROPIC_API_KEY` (repo-root `.env`, loaded by `python-dotenv`; the runner errors before any network call if it's missing) plus `BRAVE_API_KEY` (scrape runs locally, no key), exactly like the Gemma path. The `anthropic` SDK is a project dep. Run: `uv run python src/claude/run_claude.py`.

## vLLM serving (fast eval + GRPO rollouts)

The HF `model.generate` path is single-GPU and not thread-safe, which is why [scripts/eval/eval.py](scripts/eval/eval.py) **forces `--workers 1` for a local Gemma run** (a 500-episode eval took 5.4 h). vLLM fixes that (continuous batching, paged KV) and is the intended rollout engine for GRPO. Design + economics: [notes/vllm_inference.html](notes/vllm_inference.html); measured results: [notes/experiments.md](notes/experiments.md).

**Our code never imports `vllm`.** It talks to a vLLM **server** over HTTP via the `openai` client, so `openai` is the only import dep (plus explicit `jmespath`, which TRL's tool-calling GRPO needs). `vllm` is a **pod-side serve dependency** — install it in a **separate venv** (it drags its own torch, which would fight this repo's `cu128` pin), never into `.venv`.

**Two serving paths, deliberately different:**

- **Teacher / any model with a vLLM tool-call parser** → `--model vllm` on [scripts/eval/eval.py](scripts/eval/eval.py) (`--base-url`, `--served-model-name`), driving [src/serving/openai_agent.py](src/serving/openai_agent.py)'s `run_episode` (OpenAI chat + `tools=`).
- **The Gemma student** → `--model gemma --gemma-vllm-base-url <url>`, which renders with **our own** `apply_chat_template` and parses with **our own** `tokenizer.parse_response`, sending the string to raw **`/v1/completions`** (`build_gemma_completions`). Do **NOT** put the student on the chat/tools path: vLLM ships no Gemma-4 tool-call parser, and re-templating would drift from the exact wire format it was SFT'd on. vLLM strips the `stop` string, so `build_gemma_completions` re-appends `<tool_call|>` or `parse_response` won't see a complete tool call. Plumbed via `generate_turn(..., vllm_generate=...)` in [src/gemma/agent.py](src/gemma/agent.py) — **HF `model.generate` remains the default**; `model` may be `None` on the vLLM path (tokenizer-only).
- **Workers:** `eval.py` only forces 1 worker for the *local HF* gemma path; both vLLM paths default high (16) since the server is concurrent.

**Teacher serving (Qwen3-235B) — the self-hosted SFT teacher, validated end-to-end 2026-07-19.** The v2 teacher (was the Sonnet API) is now `Qwen/Qwen3-235B-A22B-Instruct-2507-FP8` on vLLM; `build_corpus.py --teacher vllm --teacher-base-url <url> --teacher-model teacher` drives it via `openai_agent.run_episode` — **the repo side was already wired, nothing to build**. Recipe: [scripts/infra/serve_teacher.sh](scripts/infra/serve_teacher.sh) (`bash serve_teacher.sh <model> <tp>`); [scripts/infra/smoke_teacher.py](scripts/infra/smoke_teacher.py) is the one-episode gate (`Pagliacci, Seattle` → schema-valid menu, exit 0/1) to run before any paid build. Provision with `scripts/infra/runpod_create.py --gpu "NVIDIA H100 80GB HBM3" --gpu-count 4 --disk 400` (**TP=4 divides the model's 4 KV heads cleanly**; 235 GB FP8 fits 4×H100/320 GB; ~$11.96/hr; driver 580/CUDA 13 via `allowedCudaVersions`, exactly as for Gemma). What mattered (measured on 4×H100):

- **Serve flags:** `--enable-auto-tool-choice --tool-call-parser hermes` (Qwen3 tool calls are Hermes-format — this is what makes vLLM surface `tool_calls`); **NO `--reasoning-parser`** (Instruct-2507 has no `<think>`; add `deepseek_r1` only for a `*-Thinking-2507` variant); `--enforce-eager` (scrape-bound teacher, not compute-bound → skip torch.compile + CUDA-graph capture for faster start and ~10-20 GB less VRAM on the tight fit). `head_dim` is a non-issue on vLLM here too. The 235 GB download was ~150 s (~1.5 GB/s; unauthenticated HF is fine, no `HF_TOKEN` needed).
- **The one real gotcha — block-scale FP8 backend selection.** Qwen3-*-FP8 is *block-scale* FP8. vLLM 0.25.1 defaults its dense block-scale GEMM to FlashInfer, but the `runpod/pytorch` image has **no FlashInfer cubin** (`VLLM_HAS_FLASHINFER_CUBIN=False`), **no `nvcc`**, and **no `deep_gemm`** — so `/v1/models` comes up **HEALTHY and the FIRST real request crashes the engine**: `RuntimeError: Assertion failed: !cubin.empty() || isPathValid(path_)` (flashinfer `fp8_blockscale_gemm_sm90`), GPUs then free to 0 and the port stops listening. Fix (baked into serve_teacher.sh): `export VLLM_BLOCKSCALE_FP8_GEMM_FLASHINFER=0 VLLM_USE_DEEP_GEMM=0` → the dense FP8 GEMM routes to compiled-in **CUTLASS** (no cubin/nvcc), the MoE to **Triton** (needs `ptxas`+`ninja`, both shipped in the wheel; keep the venv `bin/` on `PATH`). Harmless on bf16 models, so always set. A passing `/v1/models` is NOT proof it serves — the smoke (a real inference) is.

**HARD REQUIREMENTS (measured 2026-07-15 on an H200 and 2026-07-16 end-to-end on a CUDA-13 A100 — get these wrong and nothing serves):**

- **`head_dim=512` is a NON-ISSUE on vLLM, on Hopper AND Ampere.** vLLM recognises Gemma-4's mixed 256/512 heads and picks a backend that can serve them. On **Hopper (H200)**: `Gemma4 model has heterogeneous head dimensions (head_dim=256, global_head_dim=512). Using FA4 for all layers`. On **Ampere (A100)**, FA4 is unavailable (it's Hopper/Blackwell-only) and vLLM **falls back cleanly**: `FA4 not available, forcing TRITON_ATTN backend` — it still serves. So Ampere is viable (A100 $1.39/hr vs H200 $3.59/hr matters for GRPO rollouts); TRITON_ATTN-vs-FA4 *throughput* is unmeasured, but it runs. The FA2/SDPA saga in "Hardware constraints" is an **HF-only** problem — do not re-litigate it for vLLM.
- **On Ampere, launch vLLM with the venv's `bin/` ON `PATH`, not by absolute path.** TRITON_ATTN JIT-compiles its kernels and shells out to **`ninja` by name**; `/opt/vllm-env/bin/vllm serve ...` does not activate the venv, so `PATH` lacks `/opt/vllm-env/bin` and the engine dies late (after weights load and CUDA graphs capture) with a bare `FileNotFoundError: [Errno 2] No such file or directory: 'ninja'` — even though `ninja` **is installed** right next to the `vllm` binary. Use `env PATH=/opt/vllm-env/bin:$PATH vllm serve ...`. Hopper/FA4 never compiles Triton kernels, so it never hits this.
- **You need vLLM ≥0.20 AND an NVIDIA driver ≥580 (CUDA 13).** Gemma-4 support and the `cu130` torch build shipped together, so **no version pin escapes the driver requirement**:

  | vLLM | torch | Gemma-4 support |
  |---|---|---|
  | 0.12.0 | 2.9.0+cu128 | ✗ |
  | 0.18.1 | 2.10.0+cu128 | ✗ |
  | 0.20.2 / 0.21.0 / 0.22.1 / 0.25.1 | 2.11.0+**cu130** | ✓ |

  The driver is a **HOST** property (containers inherit it via the NVIDIA runtime) — **choosing a "CUDA-13 image" does NOT help**. A CUDA-12.8 host (driver 570.x) cannot serve Gemma-4 on vLLM at any vLLM version. Symptom if you get this wrong: `RuntimeError: The NVIDIA driver on your system is too old (found version 12080)`.

  **How to actually get a ≥580 host on RunPod: `runpodctl` CANNOT do it** — `create pod` has no CUDA/driver flag ([runpodctl#253](https://github.com/runpod/runpodctl/issues/253)), which is why every pod we launched by CLI landed on CUDA 12.8. The **REST API** accepts **`allowedCudaVersions`** (enum: `'13.0'`,`'12.9'`,…,`'11.8'`), and that is the only lever. Use **[scripts/infra/runpod_create.py](scripts/infra/runpod_create.py)**, which wraps `POST https://rest.runpod.io/v1/pods` with `allowedCudaVersions: ["13.0"]`:

  ```bash
  uv run python scripts/infra/runpod_create.py --name gemma-vllm --gpu "NVIDIA A100 80GB PCIe"
  uv run python scripts/infra/runpod_create.py --dry-run     # inspect the request body
  ```

  Verified 2026-07-16: the filter yields **driver 580.126.20 / CUDA 13.0** on the *same* `cu1281` image — reinforcing that the image is irrelevant and only the host filter matters. (Two API gotchas: RunPod's GraphQL sits behind Cloudflare and **403s urllib's default User-Agent** — send `curl/8.4.0`; and GraphQL wants `?api_key=`, not a Bearer header. The REST API takes `Authorization: Bearer`.)
- **Merged SFT checkpoints cannot be served on vLLM's multimodal path.** [scripts/train/train_sft.py](scripts/train/train_sft.py)'s `_save_outputs` writes model + tokenizer only, so there is no `preprocessor_config.json`; vLLM sees `Gemma4ForConditionalGeneration`, calls `AutoProcessor`, and dies (`Can't load feature extractor`). Neither the S3 base copy nor the HF cache carries that file. **Fix: [scripts/train/to_text_only.py](scripts/train/to_text_only.py)** rebuilds a text-only `Gemma4ForCausalLM` (7.46B params, vision/audio towers dropped) — the class to target anyway, since we never use the towers, and it needs no processor.
- **`--base` is REQUIRED for vLLM, or the serve dies on missing weights.** Gemma-4 E4B sets `num_kv_shared_layers=18`: its last 18 of 42 layers reuse K/V from an earlier layer, so **transformers never instantiates their `k_norm`/`k_proj`/`v_proj`** and silently drops those **54 tensors** when loading the base (2130 → 2076). That is invisible under transformers and harmless to HF eval (they are genuinely dead weights), but **vLLM builds a fused `qkv_proj` + `k_norm` for every layer** and hard-fails: `ValueError: Following weights were not initialized from checkpoint: {'model.layers.24..41.self_attn.k_norm.weight', ...}`. `--base` copies those tensors raw out of the base checkpoint. **Corollary: `to_text_only.py`'s `missing=0 unexpected=0` is a FALSE ALL-CLEAR** — it only proves transformers' own expectations were met, not that the checkpoint is complete. Don't "fix" this by disabling vLLM's `enable_weights_track` (that trades a clean error for uninitialized memory). See [notes/experiments.md](notes/experiments.md).

  ```bash
  # once, per checkpoint -- --base is not optional if you intend to serve on vLLM
  uv run python scripts/train/to_text_only.py /path/merged /path/merged-text --base /path/base-model/gemma-4-E4B-it
  vllm serve /path/merged-text --served-model-name gemma-menu --max-model-len 40960 --gpu-memory-utilization 0.85
  ```

- **Serve the merged bf16 checkpoint, never 4-bit base + adapter** (the v1 QLoRA-fidelity finding: an adapter trained on a bf16 base misbehaves on a 4-bit base — 4-bit serving alone cost ~32 points of success rate; see [notes/experiments.md](notes/experiments.md)).

### GRPO (`--use-vllm`) is a DIFFERENT setup from serving — don't copy the eval recipe

- **ONE unified cu130 env, not two.** Eval talks to a vLLM **server** over HTTP, so vLLM lives in its own venv (CLAUDE.md's "never install vllm into `.venv`" rule). TRL's GRPO **colocate** mode imports `vllm` **in-process** alongside the trainer, so vLLM + torch + trl MUST share one env. Build it vLLM-first so it pins the stack, then add the rest — the repo's `torch>=2.11.0` is satisfied by vLLM's cu130 wheel, and on a CUDA-13 host cu130 is the *correct* build (the `cu128` pin in [pyproject.toml](pyproject.toml) is a dev-box convention, not a requirement):

  ```bash
  python -m venv /opt/grpo && /opt/grpo/bin/pip install vllm==0.25.1   # pins torch 2.11+cu130
  /opt/grpo/bin/pip install "trl>=1.5.1" "peft>=0.19.1" "accelerate>=1.13.0" "bitsandbytes>=0.49.2" jmespath datasets
  /opt/grpo/bin/pip install requests python-dotenv playwright markdownify beautifulsoup4 jsonschema
  /opt/grpo/bin/playwright install --with-deps chromium
  ```

  Verified 2026-07-16: resolves to torch 2.11.0+cu130 / vllm 0.25.1 / **trl 1.8.0** / peft 0.19.1 / transformers 5.14.1, and TRL 1.8.0 still accepts the 1.5.1-era GRPOConfig fields (`max_tool_calling_iterations` et al).
- **Point `--model-path` at the `merged-text` (backfilled, text-only) checkpoint, NOT `merged`.** **TRL colocate loads vLLM from the model PATH on disk** — it does *not* build the vLLM engine by syncing the in-memory HF policy. So both vLLM gotchas above apply to GRPO exactly as they do to `vllm serve`: pointing at raw `merged` dies with `OSError: Can't load feature extractor for '/workspace/merged'` (the missing `preprocessor_config.json`, via `vllm/multimodal/processing/context.py`). `merged-text` fixes both at once — text-only class (no `AutoProcessor`) *and* the 54 backfilled tensors. `load_policy_model`'s HF-side load is happy with it too (it drops the 54 as unexpected, which is correct — they're dead weights).

  ```bash
  uv run python scripts/train/to_text_only.py /workspace/merged /workspace/merged-text --base /workspace/kv
  /opt/grpo/bin/python scripts/train/train_grpo.py --data data/grpo/train.jsonl \
      --model-path /workspace/merged-text --use-vllm --vllm-mode colocate ...
  ```

- **DO NOT run for real at the default `--max-completion-length 8192`.** TRL's tool loop *rolls back* any tool result that would push the completion past the budget and drops that sample out of the loop — so the rollout ends on a dangling tool call and **never emits a final answer**: structure/found/grounding all score 0. One capped scrape is `MAX_TOOL_CHARS`=24K chars ≈ 7.3K tokens, so 8192 fits exactly ONE. Every episode that reads two pages scores zero, and group-relative advantage then actively teaches "answer after one scrape or don't explore" — the opposite of the persistence the SFT stage distilled, and it would resurface as the v1 empty-output failure. The binding constraint on raising it is the **retained logits chain in the loss backward, ~3.5× the single fp32 logits tensor** (bf16 logits → `.float()` copy → log-softmax all retained by autograd, then a same-size grad buffer in `backward()`; the bare tensor is `bs × len × 262144 × 4B`). Measured 2026-08-08 on an H200 141 GB in colocate: **bs=1 @ 24576 does NOT fit at ANY `vllm_gpu_memory_utilization`** (~85 GB of logits-chain memory + policy 15 GB + vLLM; two OOMs, both in `accelerator.backward()` — shrinking vLLM just let the retained chain grow further before the same 24 GB ask failed). **The working H200 config is bs=1 @ 16384 + `--vllm-gpu-memory-utilization 0.18`** (~114 GB peak, ~25 GB headroom; `clipped_ratio` stayed 0 — 16384 is not binding in practice). Trade batch for length (`--per-device-train-batch-size 1` + more `--gradient-accumulation-steps`); 8192 is a SMOKE value.

## Model access

`google/gemma-4-E4B-it` is **gated**. First load requires `huggingface-cli login` with a token from an account that has accepted the license on the model's HF page. Weights cache to `~/.cache/huggingface/hub`.
